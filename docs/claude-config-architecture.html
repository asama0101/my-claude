この文書は、~/.claude/ の Claude Code 設定がどんな部品で構成され、なぜ TDD 品質規律レイヤーが必要かを、初読者向けに解説する。読む順は §1 五層構造 → §2 入口の分岐 → §3 参照関係図 → §4 実行役 → §5 チェックポイント詳細 が分かりやすい。

第一条

五層の役割分担 — 憲法・背骨・品質規律レイヤー・実行役・正典

この設定は「誰が・何を・どの順で」を5つの層に分けて持つ。各層は自分の責務だけを記述し、詳細は下の層へ委譲する。同じ定義が二箇所に現れないことが、この構成の要。2026-07-25 の全面再設計で最も重要な変化は、駆動ループ（工程の順序そのもの）の所有者が tdd-gates から superpowers のスキルチェーンへ移り、tdd-gates は自前のループを持たない薄い上乗せレイヤーになったこと — 下の「背骨」と「品質規律レイヤー」の2枚がその分離を表す。

憲 法

~/.claude/CLAUDE.md

理念・行動規範・確認と禁止・作業の進め方（規模で工程の深さを変える入口分岐）・エージェント/スキル索引。手順の詳細は持たず、正典への委譲だけを書く（例: チェックポイントの詳細は正典 checkpoints.md に委譲）。

背 骨

superpowers（プラグイン）

brainstorming → writing-plans → (subagent-driven-development｜executing-plans) → finishing-a-development-branch。要件整理・計画・実装・完了判断の駆動ループそのものを持つ完成されたスキルチェーン。Generator/Evaluator 分離・5ラウンド fix loop・progress.md・モデル格上げをネイティブに備える。

品質規律レイヤー

skills（1本）

tdd-gates＝自前の駆動ループを持たない。背骨の各ステップに寄生するチェックポイント（CP-A〜F）を差し込み、証拠不信の原則・5次元専門レビュアー・0–3点採点語彙＋Critical即FAILを上乗せするだけの薄いレイヤー。

実 行 役

agents（12本）

planner／tdd-implementer／tdd-evaluator／5次元 review-*／dev-python／doc-updater／doc-verifier／trivial-executor。各自は差分となる責務だけを持ち、共通手順は references を読む。

正 典

references・templates

agents/references/（11本＝doc-* 5・python-* 4・planner・review）＝深い作法・共通骨格。skills/tdd-gates/references/＝CP定義・採点基準・言語プロファイル。skills/tdd-gates/templates/（新設6本）＝ superpowers 側テンプレへの差分追記／差し替えプロンプト。定義の「単一の真実源」。

単一ソース規約 — 「その定義はどこが正か」を一箇所に固定する
  • CP 定義・Critical 条件 → skills/tdd-gates/references/checkpoints.md（CLAUDE.md からも正典委譲）
  • 採点閾値・スコアカード形式 → skills/tdd-gates/references/scoring.md
  • CP対応表（背骨への寄生地図・駆動順序） → skills/tdd-gates/SKILL.md（checkpoints.md は重複掲載しない）
  • 行数・ネスト深さ等の数値基準 → review-maintainability（dev-python・planner・checkpoints.md が参照）
  • レビューの共通手順・出力形式 → agents/references/review.md（5本の reviewer が共有）
第二条

作業の進め方 — 規模で工程の深さが決まる

変更規模で最初に分岐し、規模で変えるのは「委任するか否か」ではなくパイプラインの深さ。迷ったら substantial（安全側）に倒す。旧来の専用「台帳」（.tdd-gates/ledger-<slug>.md）は廃止済み — CP-A／CP-B はスコアカード応答自体が記録として完結し、CP-C 以降は superpowers（SDD／executing-plans）の progress.md に証拠行（RED/GREEN コマンドと出力）を追記する形に統一された（詳細は末尾の用語集）。

入口区分定義工程（→ 呼ばれる skill / agent）
trivial 数行・既存パターン踏襲・テスト不要（設定/ドキュメント/コメント/誤記） trivial-executor（haiku）へ一括委任。Plan モード・reviewer 群は省略可。doc 編集は trivial-executor 実行後に doc-verifier で整合確認する
small trivial 超だが substantial 未満（差分小・既存テストあり・公開インターフェース不変） 着手前は substantial と仮置きして tdd-gates に入れる。CP-B（writing-plans の計画品質レビュー時）で tdd-evaluator が4条件（差分≤2ファイル・実装差分≤50行・公開IF不変・既存テスト被覆）を照合し判定。該当すれば CP-C（RED→GREEN 中心）の簡略パイプに降格するが、CP-C の Critical（実失敗ログ）はいかなる場合も省略しない
substantial 新規ロジック・複数ファイル横断・公開インターフェース変更・非自明なバグ修正 Plan モード（superpowers の brainstorming → writing-plans）→ tdd-gates の CP-A〜D をフルで通す。採点は実装者と別コンテキストで自己承認を排除
レビュー単独 フル工程は不要だがレビューだけ独立して欲しい Main が review-* を並列起動 → tdd-evaluator が集約採点（reviewer は自分で起動しない）
第三条

参照関係図 — 誰が誰を起動し、誰が何を読むか

図は2枚に分けた。図①は起動フロー（誰が誰を起動するか）、図②は参照フロー（誰がどの正典を読むか）。図①の帯構成が今回の再設計の核心 — 「工程書」ではなく「背骨（superpowers のスキルチェーン）」と「品質規律レイヤー（tdd-gates の CP-A〜F）」の2段になり、CP は背骨の各ステップに寄生するチップとして小さく添えられる（tdd-gates 自身が駆動ループを持つわけではない）。CP-A〜F は §5 のチェックポイント記号。

図① 起動フロー — 誰が誰を起動するか（朱＝Main 起動・実線＝背骨/チェックポイントからの起動）

朱線＝Main による起動（CLAUDE.md の作業の進め方に従う） 実線＝背骨のステップ or CP チップからの起動 破線＝行動規則の参照／CP チップの寄生地点 白チップ＝tdd-gates の CP（背骨に寄生する品質規律レイヤー）

図② 参照フロー — 誰がどの正典を読むか（破線＝Read・点線＝所見の受け渡し）

破線＝正典の参照（Read） 点線＝レビュー所見の受け渡し 破線枠＝ディレクトリのまとまり 白チップ＝個別ファイル
pytest は意図的に「二枚」ある skills/tdd-gates/references/profiles/pytest.md は薄い「CP用グルー」（パス→テスト種別・実行コマンド・合格ログ判定）。深い作法は agents/references/python-testing.md が単一ソースで、グルー側が委譲する。tdd-implementer は両方、dev-python は後者のみを読む。
新言語は _template.md から拡張する 言語プロファイルは現状 pytest のみ。未対応言語では profiles/_template.md から起草し、テスト実行コマンドと合格ログ形式をユーザー承認後に CP-C を開始する（pytest 前提で進めない。未確定のまま進めそうになったら GUARDRAIL_HALT: profile_undefined で停止する）。
UI/UX は独立ゲートを持たない 旧 Gate 7（UI/UX レビュー）は独立チェックポイントとして残らず、CP-C の条件付き検査に統合された。テスト種別が unit 判定でも、対象にテンプレート/ルーティング/ビュー層の変更が含まれれば frontend-design スキル＋敵対的クロスレビューを追加起動する（図①では CP-C チップ脇の注記で表示）。
tdd-gates を通らない変更でも doc 同期の委任は働く tdd-gates を通らない変更でも、CLAUDE.md のタスク手順が同じく doc-updater への委任を課す（ユーザー受け入れ OK 後に実行）。
数値基準の横断参照は図に引いていない 関数50行・ファイル800行・ネスト4 等の数値基準の正典は review-maintainability で、dev-python・planner・checkpoints.md が参照する（§1 の単一ソース規約）。agent 間の横断エッジは図が混むため、この脚注で代える。
条件付き並列レビューとレビュー役の分岐は図に引いていない CP-B の security/perf 敏感タスクに対する条件付き並列（最大2本）、CP-D の review-*5本→tdd-evaluator集約、CP-E（レビュー役=tdd-evaluator）と CP-F（レビュー役=doc-verifier）の使い分けは、図の煩雑化を避けこの脚注で代える。詳細は checkpoints.md 各CP節。

第五条

チェックポイント CP-A〜F — 背骨に寄生する6つの検査点

「動くように見えて中身がバグだらけ」を防ぐ工程そのもの（駆動ループ・fix loop・進捗記録）は、もう tdd-gates が持たない。superpowers のスキルチェーンが背骨として工程を進め、tdd-gates はその決まった寄生地点にチェックポイント（CP-A〜F）を差し込むだけ。CP-A・CP-B は tdd-gates 独自の PASS/CONDITIONAL/FAIL で判定するが、CP-C 以降は SDD（subagent-driven-development／executing-plans）純正のリトライ機構にそのまま従う（tdd-gates 独自の再評価カウンタは持たない）。カードの SDD 5ラウンド fix loop のようなチップは、そのCPの差し戻しが tdd-gates 独自ではなく SDD 純正のリトライ機構に従うことを示す。番号が朱の CP は Critical が特に要となる工程。

A

要件ギャップレビュー

CP-Abrainstorming に寄生

依頼＋既存コード・ドメイン・制約を分析し、要件を抽出・構造化して抜け漏れなく確定する（受入基準の言語化・テスト設計は CP-B）。brainstorming の Spec Self-Review 後・User Review Gate 前に挿入し、土台は superpowers 同梱の spec-document-reviewer-prompt.md への差分追記（templates/spec-gap-review-addendum.md）。

brainstorming 起草tdd-evaluator 採点
Critical: ①コンテキスト把握が的確 ②要件の網羅性 — evaluator が抜け漏れ候補を敵対的に列挙し、非自明な欠落はユーザー確認（Stop & Ask）で解消 ③スコープが単一。

判定: tdd-gates 独自 PASS/CONDITIONAL/FAIL（最大2回）。専用台帳は持たず、spec 文書自体（brainstorming が commit）とスコアカード応答が記録になる。

B

計画品質レビュー

CP-Bwriting-plans に寄生

CP-A で確定した要件を検証可能な受入基準・テストシナリオへ言語化し、実装着手前の既存コード・セキュリティ・分離リスクを監査する。writing-plans の Self-Review 後・Execution Handoff 前に挿入し、土台は同梱の plan-document-reviewer-prompt.md への差分追記（templates/plan-quality-review-addendum.md）。small/substantial の4条件判定もここで行う（差分≤2ファイル・実装差分≤50行・公開IF不変・既存テスト被覆）。security/perf 敏感タスクには review-security／review-performance を条件付き並列（最大2本）。

writing-plans 起草tdd-evaluator 採点（既定単独）
Critical: 受入基準↔要件↔シナリオのトレーサビリティに漏れがない（各要件に最低1受入基準・各受入基準に最低1シナリオ）／重大セキュリティ欠陥・設計破綻がない。

判定: tdd-gates 独自 PASS/CONDITIONAL/FAIL（最大2回）。専用台帳は持たず、plan 文書自体とスコアカード応答が記録になる。

C

タスク証拠検証

CP-CSDD/executing-plans に寄生SDD 5ラウンド fix loopsmall ルートは簡略可

RED（失敗するテストを先に書く）→GREEN（最小実装）→REFACTOR（振る舞い不変で整理）の各段階を、実行ログに基づいて検証する。SDD/executing-plans の「### 3. Review the task」で標準ディスパッチされる task-reviewer-prompt.md を tdd-evaluator に差し替える（templates/task-evidence-addendum.md）。実装作業自体は SDD の implementer subagent（tdd-implementer）がそのまま担う。

最大の付加価値（明示的な上書き）: SDD 標準の task-reviewer-prompt.md には "Do not re-run the suite to confirm their report."（実装者の報告を信頼し再実行しない）とあるが、tdd-gates はこれを明示的に上書きする。tdd-evaluator は RED/GREEN のテスト実行結果を実装者の報告のまま信用せず、必ず自ら再実行して確認する。
tdd-implementer 実装tdd-evaluator 検証（task-reviewer 差替）
Critical: RED＝evaluator が自ら再実行し実際に失敗（無条件失敗・偽装は無効）＋差分がテストファイルのみ。GREEN＝自ら再実行し全緑＋RED時点のテストと同一（assert 骨抜きなし）＋最小実装。REFACTOR＝新機能混入なし・テストファイル不変・全緑。UI/UX はテンプレート/ルーティング/ビュー層変更時に unit 申告でも回避不可で条件付き追加。security/perf は CP-C 自身が判定せず、CP-B が付けたタグを見て該当タスクにのみ追加起動する。

証拠は SDD の progress.md に証拠行（RED/GREEN コマンドと出力）として追記する（tdd-gates 独自の台帳は作らない）。

D

最終スコアカード

CP-DSDD Final Review に寄生SDD Final Review（1修正波+1 re-review）

変更差分全体を多次元で採点し、マージ可否を判定する最終ゲート。SDD の「## Final Review」が標準ディスパッチする code-reviewer.md の単独レビューを、review-*5本並列起動＋tdd-evaluator集約に差し替える（templates/final-scorecard-review-prompt.md）。各 reviewer は所見を scratchpad の所見ファイルに直接書き出し、tdd-evaluator がそのファイル群を自ら Read して集約する（Main は所見本文を要約・改変しない）。

correctnesssecurityperformancemaintainabilitytest→ tdd-evaluator 集約
Critical: 仕様不適合ゼロ・既存回帰ゼロ・偽装テスト検出ゼロ（assert なし・常に真・実装の写経。目視に加えミューテーション検証必須 — 徴候があれば該当テスト、無くても代表1件にスモーク）。
E

CI 品質ゲート整備

CP-ECI 運用時のみSDD 通常タスクループ

CI が必須ステージ（lint・typecheck・build・unit・integration・主要 E2E）を自動実行するよう整備・検証する。writing-plans が条件を満たせば計画の末尾タスクとして自動追加（templates/ci-gate-task-template.md）し、追加後は CP-C と同じ SDD の通常タスクループに乗る — CP-E 自体は独自のディスパッチ・リトライ機構を持たない。プロファイル駆動 — 具体コマンドは言語プロファイルが供給する。「グリーン」は push 後の非同期事象のため、本CPは定義の存在・被覆をゲートする。

doc-updater 実装tdd-evaluator 採点（CP-Cの仕組みに乗る）
Critical: 必須ステージ（lint・typecheck・build・unit・integration・主要E2E）がすべて CI 定義に含まれている（preview デプロイは任意のため対象外）。
F

ドキュメント同期

CP-Fdoc 影響なしならスキップSDD 通常タスクループ

README・ガイド・コードマップ・API 仕様を変更内容に同期する。CP-E タスクの後、writing-plans が同様に計画末尾へ自動追加するタスク（templates/doc-sync-task-template.md）。実装タスクとしては CP-C と同じ SDD の通常タスクループに乗るが、レビュー役だけが tdd-evaluator ではなく doc-verifier になる（執筆者と検証者の分離を保つため）。

doc-updater 執筆doc-verifier 整合確認（別コンテキスト）
Critical: doc-verifier の照合で、裏付けの無い事実主張（実装に無い挙動・根拠の無い数値の記載）が未解消のまま残っている。
✓
ユーザー受け入れ確認 — CP-A→B→C→D→E→F を1サイクルとして自動で通し、受け入れ確認はCP-F 完了後に一度だけ行う。CP-A/B の CONDITIONAL 再評価や CP-C〜F の SDD fix loop は例外処理でなく正規工程として自動で回り、都度のユーザー承認は挟まない — 正常系で人間が止まるのはこの一点のみ。この時 tdd-evaluator が受け入れチェックリスト（受入基準＋CP-Dの5次元＋CP-E/Fの整備状況＋例外処理・権限漏れ・変更影響範囲）を生成して返す。NG なら該当 CP へ差し戻す。複数マイルストーン計画では、マイルストーン単位で CP-F まで自動通しし、各マイルストーンの CP-F 後 1 回の受け入れ確認に一本化する（マイルストーン間の中間確認はしない）。止まるのはガードレール発動時のみ（非自明な要件抜け漏れ・再評価/fix loop 上限到達による FAIL 確定・仕様の曖昧化）— 構造化フォーマットは §6 の GUARDRAIL_HALT を参照。
第六条

判定と検印 — スコア率を Critical が上書きする

採点は必ず tdd-evaluator が scoring.md 準拠で行う。重要なのは、スコア率がどれだけ高くても Critical 1件で即 FAIL になること — 「点数を稼いで欠陥をすり抜ける」経路を断つ。この即FAILルールは全CP共通だが、判定の見た目（フォーマット）は2種類に分かれる。

下の3つの判子は CP-A／CP-B にのみ適用される（tdd-gates 独自の PASS/CONDITIONAL/FAIL・最大2回の再評価）。

合PASS

PASS

スコア率 80% 以上かつ Critical 全達成。スコアカードの各 PASS には evaluator 自身が再実行した検証コマンドの出力行の添付が必須 — 実行痕跡のない PASS は無効。

条CONDITIONAL

CONDITIONAL

スコア率 60–79%。差し戻して再評価するが上限 2 回。再評価では前回スコアカードの指摘を1件ずつ引用し解消／部分解消／未解消で判定 — 引用なし・カウンタ不整合は上限到達扱い（無限往復の防止）。

否FAIL

FAIL

スコア率 60% 未満、または Critical 未達（他が満点でも即 FAIL）、または CONDITIONAL 2 回超。工程を差し戻す。

CP-C 以降は SDD 互換の Spec Compliance 形式で判定する

PASS/CONDITIONAL/FAIL の判子は使わず、subagent-driven-development の task-reviewer-prompt.md と同型の形式で返す — ✅ Spec compliant ／ ❌ Issues found ／ ⚠️ Cannot verify from diff の3値と、指摘を Critical（Must Fix）／Important（Should Fix）／Minor（Nice to Have） に分ける。tdd-gates 標準の SDD reviewer と違う点は、Critical 判定の根拠を主観でなく checkpoints.md の該当 Critical 行に紐付けること。差し戻し・再評価は tdd-gates 独自のカウンタではなく、SDD 純正のリトライ機構（CP-C＝5ラウンド fix loop、CP-D＝Final Review の1修正波+1 scoped re-review）にそのまま従う。

停止シグナル — GUARDRAIL_HALT（ガードレール停止）

前提不足・自動化ループの上限到達による停止は、曖昧な自然文でなく GUARDRAIL_HALT: <reason_code> 形式で構造化する。本文には不足・曖昧な項目（missing/ambiguous）とユーザーが選べる選択肢（options）を必ず列挙する。reason_code は3種のみ — requirement_gap（CP-A の非自明な要件抜け漏れ）／retry_limit_exceeded（CP-A/B の CONDITIONAL 再評価が上限2回に到達してもPASSに届かない）／profile_undefined（対象言語のプロファイルが未確定）。これは「都度の承認待ち」ではない — 正常系の PASS/CONDITIONAL 進行では発火せず、前提が崩れた異常系でのみ発火する（正常系の唯一の停止点は §5 の「ユーザー受け入れ確認」＝CP-F 完了後の一度きり）。

第七条

破り方と防ぎ方 — AI 駆動開発の品質問題への14の防衛

この仕組みは「AI 実装者がどうサボり・どう取り繕うか」を先回りして設計されている。各カードは 破り方（起きうる品質問題）→ それを構造的に潰す仕組み の対。

SDD の「報告を信頼する」前提の悪用 — 実装者の自己申告だけで済ませる

tdd-gates 最大の付加価値。 SDD 標準の task-reviewer-prompt.md には "Do not re-run the suite to confirm their report."（実装者の報告を信頼し再実行しない）と明記されているが、CP-C はこれを明示的に上書きする。tdd-evaluator は RED/GREEN の実行結果を実装者（tdd-implementer）の報告のまま信用せず、必ず自ら Bash で再実行し、自分の目で確認した出力だけを証拠として採点する。

checkpoints.md（CP-C）／templates/task-evidence-addendum.md／tdd-evaluator.md

要件の抜け漏れ — 存在しない要件は誰も検査しない

CP-A で evaluator が要件集合の完全性を敵対的に点検し、抜け漏れ候補（未記載・暗黙要件・未対応エッジ）を列挙。真実源はユーザーにあるため、非自明な欠落は自動 FAIL せず GUARDRAIL_HALT: requirement_gap 形式で構造化提示して確認し、要件へ反映する。

checkpoints.md（CP-A Critical）

自己承認 — 実装者が自分で合格を出す

Generator（tdd-implementer）と Evaluator（tdd-evaluator）を必ず別サブエージェント・別コンテキストで起動。CP-D の reviewer 所見は scratchpad 経由で evaluator が直接 Read し、Main が要約・改変する経路を外す（当事者が critical 所見を軟化させる余地を消す）。

checkpoints.md / SKILL.md / tdd-evaluator.md

口先報告 — 「テストは通るはず」

証拠主義: RED / GREEN は実行コマンド＋出力スニペットを証拠として残す（CP-A/B はスコアカード、CP-C 以降は SDD の progress.md）。ログのない主張は該当項目 0 点。

SKILL.md / scoring.md

ログ捏造 — それらしい出力を貼る

evaluator は貼られたログ・差分を信頼せず、Critical 項目は自分で Bash 再実行して再現した出力のみを証拠にする。再現不能・テストパス不一致は 0 点。

tdd-evaluator.md / SKILL.md

採点者の不正 — 通したいがためにテストを直す

evaluator は Write/Edit ツールを持たず、Bash でも sed -i・リダイレクト・mv/rm・git add/commit を禁止。読取と検証実行しかできない。

tdd-evaluator.md（frontmatter 制約）

RED 偽装 — 形だけ失敗させる

assert False・トートロジー・例外 raise だけの無条件失敗は Critical 未達。collected 0 items や import ERROR で「失敗した」ことにするのも無効。

checkpoints.md（CP-C）／profiles/pytest.md

assert 骨抜き — GREEN でテストを弱める

evaluator が RED 時点で確認したテスト本文と GREEN 時点の git diff を自ら照合し、assert が弱められていないかを検査。差分があれば Critical 未達。

checkpoints.md（CP-C）／tdd-evaluator.md

REFACTOR への新機能混入

CP-C REFACTOR の Critical は振る舞い不変。evaluator が git diff でテスト不変と、既存テストから到達不能な新規の条件分岐・機能追加がないことを確認する。

checkpoints.md（CP-C）

過剰実装 — テストにない機能の作り込み

CP-C GREEN で evaluator が git diff にテストが検証しない実装分岐がないか（最小性）を確認する。

checkpoints.md（CP-C）／tdd-evaluator.md

形骸化テスト — 常に PASS する飾り

CP-D に偽装テスト検出の Critical: assert なし・常に真・実装の写経を検出したら即 FAIL。目視に加えミューテーション検証（バグ注入して落ちるか確認）を、徴候があれば該当テストに、無くても代表1件にスモークで実施する。

checkpoints.md（CP-D）

スコア稼ぎ — 点数で欠陥を薄める

Critical 即 FAIL がスコア率を上書きする。1 件でも未達なら他が満点でも FAIL（全 CP 共通）。

scoring.md

無限往復 — 差し戻しで粘る

CP-A/B のみ: 再評価は上限2回、各再評価で前回指摘の引用と整合を検査し、引用なし・カウンタ不整合は上限到達扱いで FAIL 格上げ（GUARDRAIL_HALT: retry_limit_exceeded でユーザーに差し戻す）。CP-C 以降は tdd-gates 独自の上限を持たず、SDD 純正のリトライ機構（CP-C＝5ラウンド fix loop、CP-D＝Final Review の1修正波+1 scoped re-review）が無限往復を防ぐ。

scoring.md

工程のバイパス — 監査できない工程

旧来の専用「台帳」（.tdd-gates/ledger-*.md）は廃止。CP-A/B はスコアカード応答自体、CP-C 以降は SDD の progress.md への証拠行追記が記録の正典になり、spec/plan 文書自体も superpowers が git commit する。工程飛ばしと自己承認を、背骨ネイティブの記録機構で防ぐ。

SKILL.md／checkpoints.md
第八条

Hooks — モデルの規律を機械で補強する

ここまでの防衛は「モデルが指示に従う」前提の規律。hooks はその外側で、従わなかった場合も機械的に止める最後の層。現在はすべてブロック型の4本。

hookこの仕組みとの関係
bash-guard.sh破壊的コマンド・機密ファイルの読取/持ち出しをブロック（rm/rmdir/unlink/git rm はプロジェクト配下／$CLAUDE_HOME配下／/tmp配下の子要素のみ許可）— 禁止事項（憲法）の機械的執行
workspace-guard.shプロジェクト配下／~/.claude 配下／/tmp 配下以外への Write/Edit をブロック（~/.claude/hooks/ とハーネス設定 settings.json は許可の例外・実行前確認は settings.json の permissions.ask 側で担保）— 作業範囲の執行
venv-guard.shvenv 外への pip install をブロック — 環境汚染の防止
main-branch-guard.shmain/master ブランチ上での Write/Edit/MultiEdit/NotebookEdit、および Bash の削除・変更系コマンド（rm/mv/cp/tee/touch/リダイレクト/sed -i/git commit/git rm 等）をブロック（読み取り専用コマンドは対象外）— main 直編集の禁止と、finishing-a-development-branch が担うブランチ運用への誘導
要するに — Main が憲法 CLAUDE.md の規則に従って入口を分岐し、superpowers（背骨）が要件定義から完了判断までの駆動ループを進め、tdd-gates（品質規律レイヤー）がその決まった寄生地点にチェックポイントを差し込み、agent（実行役）は実装と採点を別人格に分け、references・templates（正典）が定義の重複を許さない。その全工程を証拠つき判定（CP-A/B の検印・CP-C以降の Spec Compliance・Critical 即 FAIL）が監査し、hooks が外側から機械的に支える。「動くように見える」だけのコードが通り抜ける穴を、層ごとに一つずつ塞いだ構成になっている。
補遺

用語集 — 本文で使う略語・固有語

本文はグロスを外して用語をここに集約した。初出で意味が要るものは以下を参照。

Main
ユーザーと対話する親セッション（オーケストレータ）。全 agent の起動主体で、~/.claude/CLAUDE.md がその行動規則。
台帳（ledger）
旧来は .tdd-gates/ledger-<slug>.md という専用監査記録ファイルだったが廃止済み。CP-A/B は専用台帳を持たず、直近のスコアカード応答自体が記録になる。CP-C 以降は superpowers（SDD／executing-plans）の progress.md が記録の正典。
verdict
CP-A/B の判定結果。PASS（80%以上＋Critical全達成）／CONDITIONAL（60–79%）／FAIL（60%未満または Critical 未達）。CP-C以降はこの判子を使わず、Spec Compliance 形式（✅/❌/⚠️）で判定する。
Plan モード
実装前に計画だけ立てて承認を得る、Claude Code の読取専用モード。
Generator／Evaluator
実装役 tdd-implementer と採点役 tdd-evaluator の本文中の呼称。
opus／sonnet／haiku
Claude モデルの階層。opus＞sonnet＞haiku の順に高機能・高コスト。
ADR
Architecture Decision Record。設計判断の記録。
3層（unit／integration／e2e）
テスト階層。unit＝業務ロジック、integration＝結合検証（最も厚くする層）、e2e＝最小限の主要導線。
SendMessage
既存エージェントへ同一コンテキストのまま追加指示を送る仕組み。
scratchpad
セッションの一時ファイル置き場。reviewer が所見を書き、evaluator が直接 Read する。
frontmatter
エージェント定義ファイル冒頭のメタデータ・制約。
グリーン
CI が成功で完走した状態。push 後の非同期事象。
Stop & Ask
非自明な要件欠落を自動 FAIL せずユーザーに確認して解消する運び。構造化フォーマットは GUARDRAIL_HALT。
GUARDRAIL_HALT
前提不足・自動化ループの上限到達時の停止を GUARDRAIL_HALT: <reason_code> 形式で構造化する仕組み。reason_code は requirement_gap／retry_limit_exceeded／profile_undefined の3種。「都度の承認待ち」ではなく異常系専用の停止点。
プロファイル駆動
具体的なテスト実行コマンド等を言語プロファイルが供給する仕組み。
CP-A〜F
tdd-gates が superpowers のスキルチェーンに寄生させる6つのチェックポイント。CP-A/B は独自 PASS/CONDITIONAL/FAIL、CP-C〜F は SDD 互換の Spec Compliance 形式で判定する。
superpowers
要件定義から完了判断までのスキルチェーンを提供するプラグイン。tdd-gates が背骨として乗るループの実体。
SDD（subagent-driven-development）
superpowers のスキルの一つ。Implementer と Task Reviewer の分離・5ラウンド fix loop・progress.md・Final Review をネイティブに持つ実装駆動ループ。
Iron Law
superpowers:test-driven-development の中核原則「NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST」。tdd-gates の規律の根拠。
brainstorming
要件定義・spec 文書を作る superpowers のスキル。CP-A が寄生する。
writing-plans
plan 文書（実装計画）を作る superpowers のスキル。CP-B が寄生し、CP-E/CP-F の末尾タスクもここで追加される。
finishing-a-development-branch
実装完了後の統合方法（マージ／PR／保留）を決める superpowers のスキル。tdd-gates の CP は寄生しない。
