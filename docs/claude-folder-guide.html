はじめに

~/.claude（実体は /home/asama/.claude）は、Claude Code の全プロジェクト共通の設定フォルダである。グローバル指示（CLAUDE.md）・権限とフックの設定（settings.json）・破壊的操作を防ぐガードスクリプト（hooks/）・タスクごとに使い分けるサブエージェント定義（agents/）・自作の補助スキル（skills/）・有効化済みの公式プラグイン（plugins/）・HTML成果物の流用元テンプレート（assets/）が置かれており、Claude Code の挙動そのものを規定している。

本ガイドは、このフォルダの中身を「用語集」「カタログ」として引くための自己完結 HTML である。Claude Code を操作しながら別タブで開き、「この agent / skill / hook は何のためにあり、いつ使われるか」を検索・ナビで素早く参照する用途を想定している。アーキテクチャ全体の設計思想・構成要素間の関係を解説する文書ではない（それは別文書 claude-config-architecture.html の役割であり、本ガイドとは目的が異なる）。

使い方: 左ペイン上部の検索ボックスに名前や説明文の一部を入力すると、一致しない項目が左ナビ・右のカード双方から絞り込まれる。左ナビの項目をクリックすると右側の該当カードへスムーズスクロールし、スクロール中は現在地のナビ項目が自動でハイライトされる。狭い画面では左ナビは左上の「☰ 目次」ボタンで開閉するオーバーレイに切り替わる。

設定ファイル

CFG-01

CLAUDE.md（グローバル）

全プロジェクトに適用されるグローバル指示。「理念」（根本解決・影響最小化・コンテキスト衛生）、「行動規範」（結論先行・即行動・進捗の実証・客観性・スコープ規律・境界・ターン終了・長時間運用・言語・再計画）、「確認と禁止」、「作業の進め方」（trivial / small / substantial の比例ルール表と手順）、「リファレンス」（エージェント一覧・スキル一覧）、「Hooks（enforcement の正典）」の構成。

いつ使うか: 全セッションで常時適用される前提知識。動作方針に疑問が生じたらまずここを確認する。

path: ~/.claude/CLAUDE.md

関連: 比例ルール表は SKL-03（tdd-gates）と対応。Hooks 表は HK-01〜04 の実体と対応。

CFG-02

settings.json

トップレベルキーは $schema, permissions, model, hooks, statusLine, enabledPlugins, effortLevel, tui, skipWorkflowUsageWarning, remoteControlAtStartup, inputNeededNotifEnabled, agentPushNotifEnabled, skipAutoPermissionPrompt。permissions は allow/deny/ask の3リスト＋defaultMode: "plan"＋disableBypassPermissionsMode: "disable"。deny は秘密鍵・認証情報ファイルの読み書きと /etc 等システム領域への Edit を禁止。ask は git push/git reset --hard 等の破壊的 git 操作と、hooks/・settings.json 自体の編集を確認対象にする。hooks.PreToolUse は4フック（HK-01〜04）を登録。model: "sonnet"。enabledPlugins は5プラグインを有効化。

いつ使うか: 権限・フック・モデル・有効プラグインの設定を確認・変更するとき。

path: ~/.claude/settings.json

関連: hooks キーは HK-01〜04、enabledPlugins はプラグインSkillsセクションに対応。

CFG-03

settings.local.json

中身は {}（空オブジェクト）。settings.json の値をマシン・ユーザー固有に上書きするためのローカル設定ファイル。現状は上書き設定なしの空状態。

いつ使うか: そのマシン・ユーザー固有の一時的な権限追加等が必要になったとき。環境固有資産のため、設定管理リポジトリの同期対象からは除外される。

path: ~/.claude/settings.local.json

CFG-04

statusline-command.sh

ステータスライン表示用シェルスクリプト。jq で入力 JSON（cwd・モデル名・effort・コンテキスト使用率・git ブランチ・5時間/週次レート制限・累計コスト）を解析し、ディレクトリ・ブランチ（OSC8 でハイパーリンク化）・モデル/effort・コンテキスト使用率バー・レート制限バー（閾値で緑/黄/赤に色分けし、リセットまでの残り時間つき）・累計コストを1行に整形して出力する。

いつ使うか: 直接使うことはない。settings.json の statusLine.command から自動的に呼ばれ、Claude Code 画面下部に常時表示される。

path: ~/.claude/statusline-command.sh

Hooks

いずれも PreToolUse で発火する fail-close 設計（jq 不在時は解析不能として一律ブロック）。settings.json の hooks.PreToolUse で、bash-guard.sh/venv-guard.sh は Bash マッチャに、workspace-guard.sh/main-branch-guard.sh は Write|Edit|MultiEdit|NotebookEdit|Bash マッチャに登録されている。

HK-01

bash-guard.sh

Bash 実行前ガード。ディスク破壊・強制再フォーマット（dd/mkfs）、権限破壊（chmod 000 等）、プロセス/システム停止（kill -9 -1・fork爆弾・shutdown系）、危険なリモート実行（curl | bash）、システムファイル破壊、DB破壊、グローバルパッケージのインストール/一括アンインストール、迂回削除（find -delete・shutil.rmtree・rsync --delete）、.ssh/シェル設定書き換え、機密ファイル（.env/秘密鍵等）の読み取りを正規表現でブロックする。クォート分割・バックスラッシュ・${IFS} 等の難読化は正規化して再判定する。rm/rmdir/unlink/git rm は、プロジェクト配下・$CLAUDE_HOME 配下・/tmp 配下の子要素のみ許可（各ゾーンのルート自体・変数展開やコマンド置換を含む対象は不許可）。

いつ使うか: 常時自動発火（Bash ツール実行前）。ブロックされたら自分で回避せず、ユーザーに ! <コマンド> 形式で実行を依頼する。

path: ~/.claude/hooks/bash-guard.sh

HK-02

venv-guard.sh

Bash 実行前ガード。pip install/uninstall・python -m pip・uv add/uv pip install が、VIRTUAL_ENV 未設定またはプロジェクト外の venv の場合にブロックする。venv バイナリを直接指定（.venv/bin/pip install ...）している場合は許可。uv 系はプロジェクト配下に .venv が存在するかで判定する。

いつ使うか: 常時自動発火。venv 外へのグローバルインストールを防ぎたいとき。誤検知は文字列一致由来のため Read で回避する。

path: ~/.claude/hooks/venv-guard.sh

HK-03

workspace-guard.sh

Write/Edit/MultiEdit/NotebookEdit/Bash への実行前ガード。書き込み許可ゾーンは「プロジェクト配下」「~/.claude 配下（hooks/・settings.json を含む。設定管理ワークフロー自体が編集を要するため自己防御なし）」「/tmp/claude-*/ 配下（セッション用一時ディレクトリ）」の3つのみ。Bash では /var/tmp や /tmp/claude-*/ 以外の /tmp 配下へのリダイレクト、および cp/tee/mv/curl/wget のプロジェクト外絶対パス宛先を保守的にブロックする（コマンド置換を含むセグメントは判定不能としてスルー）。

いつ使うか: 常時自動発火。誤検知（grep 等の read-only コマンドが文字列中に > /var/tmp/ 等を含む場合）は Read ツールで回避する。

path: ~/.claude/hooks/workspace-guard.sh

HK-04

main-branch-guard.sh

main/master ブランチ上での Write/Edit/MultiEdit/NotebookEdit、および Bash の削除・変更系コマンド（rm/rmdir/unlink/git rm/git commit/リダイレクト書き込み/tee/cp/mv/touch/sed -i 等）をブロックする。対象ファイルの git ブランチ（Write/Edit系）または cwd の git ブランチ（Bash系）が main/master ならブロック。git status/cat/ls/grep 等の読み取り専用コマンドは対象外。

いつ使うか: 常時自動発火。ブロックされたら git checkout -b <branch> でブランチを作成してから再試行する。

path: ~/.claude/hooks/main-branch-guard.sh

dev-python

path: ~/.claude/agents/dev-python.md

AG-02

doc-updater

モデル: sonnet

ドキュメントの新規作成・構成設計と、既存ドキュメントの同期更新を担う専門家。人間向けドキュメント（システム概要・運用手順・設計文書）の設計→執筆、README・ガイドのソース同期を担当する。事実は必ずソースから取得し推測で書かない（不発明制約：根拠のない数値は「未規定」と明示）。タスク種別に応じ references/doc/ 配下（source-sync / design / writing / verify / html）を必要時にオンデマンドで Read する。

いつ使うか: ドキュメントの新規整備・構成設計・既存 README/ガイド/API 仕様の更新のいずれでも積極的に活用。

path: ~/.claude/agents/doc-updater.md

関連: 整合確認は AG-03（doc-verifier）、構成・可読性確認は AG-06（review-doc-readability）に委譲する（自分では確定させない）。

AG-03

doc-verifier

モデル: sonnet

人間向けドキュメントの整合確認（記載事実 vs ソースコード）を、執筆者と別コンテキストで採点する専門家。文書から検証可能な事実（定数・閾値・ログメッセージ・CLI オプション・スキーマ等）を抽出し、grep 等でソースと1件ずつ照合して ✓/不一致で報告する。Write/Edit を持たないのは意図的で、自己承認を排除するため修正はしない（report 専用）。

いつ使うか: doc-updater または trivial-executor のドキュメント執筆・更新の後、Main から起動される。

path: ~/.claude/agents/doc-verifier.md

AG-04

planner

モデル: opus

複雑な機能実装・アーキテクチャ変更・複雑なリファクタリングの計画専門家。要件分析→アーキテクチャレビュー→ステップ分解→実装順序の決定に加え、非自明な設計判断はメリット/デメリット/代替案/決定を文書化する。フェーズ分割（最小限の価値→コア体験→エッジケース→最適化）も担当。読取専用ツールのみを持ち、最終計画は Main が組む前提の素材提供役。

いつ使うか: 機能実装・アーキテクチャ変更・複雑なリファクタリングのリクエスト時に自動的に起動する。

path: ~/.claude/agents/planner.md

AG-05

review-correctness

モデル: opus

正確性・バグ検出に特化したレビュアー。冪等性の破壊・記録前の破壊的操作・トランザクション境界・TOCTOU（CRITICAL）、条件式の誤り・オフバイワン・例外の握り潰し・リソースリーク（HIGH）、境界値・並行/再入（MEDIUM）を検査する。バグ・ロジックの正しさのみ担当し性能・セキュリティは担当外。

いつ使うか: substantial なコード変更後。他の review-* と Main が並列起動する。

path: ~/.claude/agents/review-correctness.md

AG-06

review-doc-readability

モデル: sonnet

人間向け Markdown 文書の構成・可読性を、執筆者と別コンテキストで採点する専門家。要約先出し・段落設計・箇条書きvs散文・表vs図vs本文・見出し階層・読者適合の6観点を ✓/要改善で判定する。記載事実がソースと一致するかは AG-03（doc-verifier）の担当で本エージェントは扱わない。対象は Markdown のみ（HTML成果物の視覚デザインは対象外）。修正はしない（report 専用）。

いつ使うか: doc-updater/trivial-executor の執筆・更新の後、Main から doc-verifier と並列起動される。

path: ~/.claude/agents/review-doc-readability.md

path: ~/.claude/agents/review-maintainability.md

いつ使うか: substantial なコード変更後、他の review-* と並列起動。

AG-11

tdd-evaluator

モデル: sonnet

tdd-gates（品質規律レイヤー）の Evaluator（採点役）。CP-A〜F 全チェックポイントの採点を担う——CP-A/B は brainstorming/writing-plans の文書を敵対的に検査、CP-C は実装者の報告を自ら再実行して検証、CP-D は review-*5本の所見を集約しミューテーション検証込みで最終スコアカード化、CP-E は CI 定義の被覆を採点する。0〜3点採点＋Critical即FAIL判定。自分ではコードを書かず、Bash は検証専用（ファイルを変更するコマンドは使わない）。TDD 文脈外でも単独起動して汎用スコアードレビュアーとして使える。

いつ使うか: tdd-gates の採点全般、またはレビュー単独で起動したいとき。

path: ~/.claude/agents/tdd-evaluator.md

AG-12

tdd-implementer

モデル: sonnet

superpowers:subagent-driven-development（または executing-plans）から起動される implementer サブエージェント。superpowers:test-driven-development の RED→GREEN→REFACTOR 規律を強制するペルソナとして1タスク分のテストと実装を書く。採点はしない（採点は別コンテキストの AG-11 tdd-evaluator が行う）。汎用 general-purpose subagent の代わりに implementer 役として使う。

いつ使うか: tdd-gates/SDD のタスク実行フェーズで自動起動される。

path: ~/.claude/agents/tdd-implementer.md

AG-13

trivial-executor

モデル: haiku

trivial 変更（数行・既存パターン踏襲・テスト不要）の軽量実行担当。設定/ドキュメント/コメント/明白な誤記の修正、事前確定した機械的編集を一括処理する。対象外（新規ロジック・非自明なバグ修正・公開IF変更・設計判断が要るもの）と気づいたら、勝手に進めずその旨を報告して止まる。

いつ使うか: 比例ルールの trivial ルートで Main から一括委任されるとき。

path: ~/.claude/agents/trivial-executor.md

関連: doc 編集後は AG-03（doc-verifier）で整合確認する。

AG-REF

共通参照資料（agents/references/）

各エージェント本体には中核ロジックのみを置き、詳細パターン・例集・共通手順はオンデマンド参照ファイルとして agents/references/ 配下に分離している。内訳は planner.md（ADRテンプレート・詳細計画例／AG-04用）、review.md（review-*5本の共通レビュー手順／AG-05・07〜10用）、doc/source-sync.md・design.md・writing.md・verify.md・html.md（doc-updater・doc-verifierのフェーズ別詳細／AG-02・03・06用）、python/style.md・fastapi.md・rest-api.md・testing.md（dev-python・tdd-implementerのフレームワーク別詳細／AG-01・12用）の計11ファイル。エージェント定義そのものではなく個別カード化しない。

いつ使うか: 該当エージェントが該当タスクに着手する際、本体から必要時にオンデマンドで Read する（全部を事前ロードしない）。

path: ~/.claude/agents/references/

ローカルSkills

SKL-01

codemap-python

Python コードを人間がレビューする準備として、処理フロー（エントリポイントから終わりまでの実行の流れ）を一本道で読み下せる HTML レポート一式（インデックス＋フローページ群）を生成するスキル。呼び出し先のコードをモジュール境界を越えて呼び出し箇所にその場でネスト展開し、1行ごとの解説＋具体的な動作例を添える。仕様書/要件との対応表も同じレポートに含む。バグ判定はしない（判定は review-correctness 等の役割）。

いつ使うか: 「このコードを初めて読むので地図がほしい」「PR/diffのレビュー準備をして」「処理の流れを追いたい」「構造を整理して」等の発言時。

path: ~/.claude/skills/codemap-python/SKILL.md

SKL-02

html-template-import

既存の HTML ドキュメントを流用元ライブラリ（~/.claude/assets/html-templates/）へ取り込むスキル。HTML を解析してトーン（dark/light）・レイアウト種別を要約し、<内容>-<トーン>.html の規約名でコピーし、カタログ INDEX.md に1行登録する。

いつ使うか: 「このHTMLをテンプレとして保存」「既存のHTMLを流用元に取り込んで」「作ったHTMLを再利用できるように登録」等の発言時。

path: ~/.claude/skills/html-template-import/SKILL.md

関連: AST-01（Assets：report-light テンプレート）はこのスキルで登録されたもの。

SKL-03

tdd-gates

superpowers のスキルチェーン（brainstorming→writing-plans→subagent-driven-development/executing-plans→finishing-a-development-branch）に上乗せする品質規律レイヤー。CP-A〜F のチェックポイントと、Critical即FAIL＋証拠要求の採点語彙をチェーンの各ステップに差し込む。自前の駆動ループは持たず、既存チェーンに寄生する薄いレイヤー。

いつ使うか: 「TDDで実装して」「品質ゲートを回して」「新機能を実装して（テスト付きで）」等の発言時、substantial なコード変更の着手時に積極起動する。trivial は使わず AG-13（trivial-executor）に一括委任する。

path: ~/.claude/skills/tdd-gates/SKILL.md

関連: AG-11（tdd-evaluator）・AG-12（tdd-implementer）を駆動する。

Assets

AST-01

report-light テンプレート

~/.claude/assets/html-templates/INDEX.md が管理するカタログの現行エントリ。report-light.html は light・report 系（和風監査台帳）で、明朝体見出し＋「第一条」縦ラベル＋朱の検印スタンプ、カードグリッド、スクロール表、2枚組の凡例つき SVG 関係図、縦ライン式タイムライン＋各段アコーディオン（details）、末尾に用語集（dl・2カラム）という構造・CSS特徴を持つ。用途は構造監査・設計解説・多章立ての長文レポート。

いつ使うか: 新規 HTML 成果物を作る前に doc-updater がまず INDEX.md を確認し、トーン・レイアウトが合致すればこのテンプレを流用する（Skill非依存で構造・CSSを土台に内容を差し替える）。合致するテンプレが無ければ frontend-design（SF-01）で新規デザインする。新しく作った HTML を再利用可能にしたい場合は SKL-02（html-template-import）でこのカタログへ登録する。

path: ~/.claude/assets/html-templates/report-light.html（カタログ: ~/.claude/assets/html-templates/INDEX.md）

本ガイドは作成時点（2026-07-30）の構成に基づく。プラグインは superpowers 6.2.0 等、時間経過で内容がずれる可能性がある。実ファイルとの乖離に気づいた場合はソース（各 *.md／settings.json／hooks/*.sh）を直接確認すること。
