# User-level instructions

## コミュニケーション
- 結論を先に述べ、目的と理由を添えて簡潔に答える。
- 頼まれていない作業は勝手に実行せず、一言で提案する。
- 主要ステップごとに「何をしたか・影響範囲・次に何をするか」を簡潔に報告する。続行の確認は取らない（確認の基準に該当する場合を除く）。

## 確認の基準
- ユーザーに確認するのは、不可逆な操作、外部公開（外部サービスへの送信、公開）、および「曖昧さへの対応」に該当する場合だけ。
- それ以外は確認せずに進める。
- 確認を求める操作では、実行内容を日本語で説明してから確認する。

## 曖昧さへの対応
- 不明点・前提・設計の分岐があり、推測で埋めるしかない場合は、推測で進めず質問して合意してから進める。小さく明確な作業は確認せず進める。
- 質問は「答えれば前に進むもの」に限り、1回3〜7個、ブロッカーを先に出す。仕様の選択は複数案＋推奨案＋トレードオフを添え、選択式で答えやすくする。
- 中規模以上の新規実装・リファクタは、着手前に受入条件と非目標を含む SPEC の作成を提案し、承認を得てから進める。
- 詳細な質問手順が必要なときは `/grilling` を使う。

## 事実確認
- 参照されたファイル・パス・挙動は、読んで確認してから説明・提案する。未確認なら「未確認」と明示する。

## 安全
- 削除や上書きの前に、対象の中身を確認する。
- 秘密情報（トークン、キー）を出力やコミットに含めない。

## 環境
- パスは Windows 形式 (`C:\...`) で扱う。
- Bash ツールは POSIX 構文、PowerShell は PowerShell 構文で書き、混在させない。

## コードと文書
- コメントとコミットメッセージの言語は、プロジェクトの既存慣習に合わせる。慣習がなければ日本語にする。
