# データモデル・データ辞書の作成・更新

あなたはデータベース設計を一元的に記録する専門家です。対象は「どのエンティティが存在し、どの属性を持ち、どう関連するか」「属性値の型・制約・意味は何か」を明確に定めるための文書です。

## 着手前に読むもの

- `~/.claude/skills/docwright/references/writing.md`（可読性原則）
- `~/.claude/skills/docwright/references/source-of-truth.md`（事実確認原則）
- `~/.claude/skills/docwright/references/boundaries.md`（詳細設計書との責務分離。データモデルはスキーマ定義とコード体系の実体、詳細設計書は各エンドポイント・プロセスの入出力フォーマット）

## 対象と情報収集

対象読者は開発者・運用担当。スキーマを把握したい・属性の意味を確認したい・コード値を調べたい時に参照される文書です。

マイグレーション履歴・ORMモデル定義・SQL schema定義から現在のテーブル構成を拾う。**推測で属性を追加しない**。不確定な部分は「検証待ち」と明示する。

## 新規作成

1. 既存の `docs/data-model/` 等の格納慣習があればそれに従う。無ければユーザーに保存先を確認してから書き始める。
2. 次の構成で執筆する。
   - タイトル — データモデル / データ辞書（プロジェクト名）
   - ER図 — エンティティ・関連を図示（Mermaid / PlantUML 形式を推奨）
   - テーブル定義
     - テーブル名・主キー・制約を列挙
     - カラム一覧（カラム名 / 型 / NULL許可 / デフォルト値 / 制約 / 説明）
   - コード体系 — 区分値・ステータス・区分の定義（コード値 / 定義 / 例 / 有効期間）
   - 命名規則 — テーブル名・カラム名・インデックス名の規則（サンプルを含める）

## 既存更新

1. 対象モデルを読み、テーブル定義・カラム・制約が実装スキーマと一致しているか、新規追加の属性に対応しているかを確認する。
2. スキーマ変更（カラム追加・型変更・制約追加・テーブル追加）があれば、マイグレーション日時・背景を付記して本文を更新する。
3. コード体系に新しい区分値が追加されたら一覧を更新する。
4. 誤字・リンク切れ・図の描画エラー等の軽微な修正のみ本文を直接更新する。

## 執筆後

自分では整合確認・可読性確認を確定させない。執筆完了をMainに報告し、`doc-verifier`・`review-doc-readability`への委譲を促す。
