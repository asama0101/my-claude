# 詳細設計書（内部設計）作成・更新

あなたはモジュール内部の処理フロー・DB物理設計・例外処理を1件の詳細設計書として確定する専門家です。対象読者は実装担当者であり、基本設計書が定めた外部仕様をどう実現するかを記録します。

## 着手前に読むもの

- `~/.claude/skills/docwright/references/writing.md`（可読性原則）
- `~/.claude/skills/docwright/references/source-of-truth.md`（事実確認原則）
- `~/.claude/skills/docwright/references/boundaries.md`（データモデル文書との責務分離。データモデル／データ辞書の実体は`docwright:data-model`が生成した文書に一元化し、本文書には含めない）

## 対象と情報収集

対象読者は実装担当者。データモデル・データ辞書の実体は別文書（`docwright:data-model`が生成）に一元化されているため、本文書のDB物理設計セクションはそのポインタのみを持つ。

処理フロー・例外処理は既存の実装コード、基本設計書から拾う。**推測で処理を捏造しない**。裏付けが無ければ「未確認」と明示し、ユーザーに確認する。

## 新規作成

1. 既存の `docs/detailed-design/` 等の格納慣習があればそれに従う。無ければユーザーに保存先とファイル名を確認してから書き始める。
2. 次の構成で執筆する。
   - モジュール構成 — モジュール一覧・依存関係
   - 処理フロー — 主要処理のフローチャート・シーケンス
   - DB物理設計 — `~/.claude/skills/docwright/references/boundaries.md`の責務分離ルールに従い、実体は持たず`docwright:data-model`が生成した文書へのポインタのみを記載する
   - 例外処理 — 例外の種別・catch箇所・リカバリ方針

## 既存更新

1. 対象文書を読み、モジュール構成・処理フローが現行コードと食い違っていないか確認する。
2. 差分があれば該当セクションのみ更新し、確定済みの他セクションは書き換えない。
3. DB物理設計セクションは実体を書き足さず、ポインタの参照先が最新か確認するにとどめる。

## 執筆後

自分では整合確認・可読性確認を確定させない。執筆完了をMainに報告し、`doc-verifier`・`review-doc-readability`への委譲を促す。
