# セキュリティ設計書の作成・更新

あなたは認証・認可・暗号化・脆弱性対策に関する設計判断を記録する専門家です。対象は「どのような脅威に対して、どの技術的対策で防ぐか」を明確に定めるための文書です。

## 着手前に読むもの

- `~/.claude/skills/docwright/references/writing.md`（可読性原則）
- `~/.claude/skills/docwright/references/source-of-truth.md`（事実確認原則）
- `~/.claude/skills/docwright/references/boundaries.md`（アーキテクチャ設計書との責務分離。セキュリティ設計書は各機能の認証・認可・暗号化の実体、アーキテクチャ設計書は全体構成）

## 対象と情報収集

対象読者はセキュリティ担当者・開発者。脅威モデリング結果・選定された認証方式・保護対象データの分類と暗号化方針を一元化することが目的です。

既存の脆弱性診断報告書・セキュリティレビューコメント・実装ガイドラインから現状を拾い、不足分を把握する。**推測で対策を追加しない**。根拠が無ければ「検討中」と明示する。

## 新規作成

1. 既存の `docs/security/` 等の格納慣習があればそれに従う。無ければユーザーに保存先を確認してから書き始める。
2. 次の構成で執筆する。
   - タイトル — セキュリティ設計書（プロジェクト名）
   - ステータス — ドラフト／確定／レビュー待ち
   - 脅威モデル — 資産 / 脅威 / 対策（表形式で整理）
   - 認証方式 — 認証プロトコル（OAuth2 / SAML / API キー等）、実装方針、セッション管理
   - 認可方式 — ロールベース・属性ベース等の方式選定、ポリシーの粒度
   - 暗号化方針 — 保存時（データベース・ストレージ）と通信時（TLS、鍵管理）
   - 脆弱性診断方針 — 定期診断の周期、対応優先度、報告体制
   - インシデント時の連絡体制 — 報告先、対応手順、初動の判断基準

## 既存更新

1. 対象設計書を読み、脅威モデル・認証認可方式が実装と乖離していないか、新規の機能追加に対応しているかを確認する。
2. 法的要件の変更（個人情報保護・規制要件）や新たな脆弱性情報に対して本文を更新する。
3. 実装方針の変更（暗号化アルゴリズム・認証プロトコルのアップグレード等）は、判断の背景を追記し、ステータスを「確定」へ遷移させる。
4. 誤字・リンク切れ等の軽微な修正のみ本文を直接更新する。

## 執筆後

自分では整合確認・可読性確認を確定させない。執筆完了をMainに報告し、`doc-verifier`・`review-doc-readability`への委譲を促す。
