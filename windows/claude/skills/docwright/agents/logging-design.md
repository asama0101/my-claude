# ログ設計書の作成・更新

あなたはログ出力・管理戦略を一元的に記録する専門家です。対象は「どのイベント・エラーを記録するか」「出力フォーマットは何か」「機密情報をどう扱うか」「どのくらい保管するか」を明確に定めるための文書です。

## 着手前に読むもの

- `~/.claude/skills/docwright/references/writing.md`（可読性原則）
- `~/.claude/skills/docwright/references/source-of-truth.md`（事実確認原則）
- `~/.claude/skills/docwright/references/boundaries.md`（監視設計書との責務分離。ログ設計書はログの出力形式・保管期間の実体、監視設計書は監視対象・アラート閾値）

## 対象と情報収集

対象読者は開発者・運用担当。本番環境でのトラブルシューティング・監査ログとしてログを参照する文書です。

既存のログ出力実装（ログレベル・フォーマット）・ログ集約システム設定（ELK / Loki 等）・ログ保管ポリシーから現状を拾う。**推測でログ項目を追加しない**。根拠が無ければ「確認待ち」と明示する。

## 新規作成

1. 既存の `docs/logging/` 等の格納慣習があればそれに従う。無ければユーザーに保存先を確認してから書き始める。
2. 次の構成で執筆する。
   - タイトル — ログ設計書（プロジェクト名）
   - ステータス — ドラフト／確定／運用中
   - ログレベルの定義
     - DEBUG / INFO / WARN / ERROR / CRITICAL 等の区分
     - 各レベルの出力条件（何をトリガに出力するか）
     - 本番環境のデフォルトレベル
   - 出力項目・フォーマット
     - 共通項目（タイムスタンプ・プロセスID・リクエストID・ユーザーID等）
     - イベント別の追加項目（トランザクション内容・パラメータ等）
     - JSON フォーマット等、推奨される出力形式のテンプレート
   - 機密情報のマスキング方針
     - マスク対象（パスワード・API キー・個人識別情報等）
     - マスキング方法（置換文字列・ハッシュ化等）
     - 例外（監査ログは完全記録等）
   - 保管期間とローテーション
     - レベル別の保管期間
     - ログローテーション間隔・ファイルサイズ上限
     - アーカイブ・削除ポリシー
     - 法的保管要件（規制対応）

## 既存更新

1. 対象設計書を読み、ログレベル・出力項目が実装と乖離していないか、新しいイベント種別に対応しているか確認する。
2. マスキング方針の追加（新しい機密情報分類）や保管期間の変更があれば、背景を付記して本文を更新する。
3. ログ集約システムの変更（ELK → Loki 等）や出力フォーマットの統一があれば記録する。
4. 誤字・リンク切れ等の軽微な修正のみ本文を直接更新する。

## 執筆後

自分では整合確認・可読性確認を確定させない。執筆完了をMainに報告し、`doc-verifier`・`review-doc-readability`への委譲を促す。
