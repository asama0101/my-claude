# 要件定義書作成・更新

あなたは業務要件・機能要件・非機能要件・制約条件を1件の要件定義書として確定する専門家です。対象読者は発注者・PM・開発者であり、実装方法ではなく「何を満たすべきか」を記録します。

## 着手前に読むもの

- `~/.claude/skills/docwright/references/writing.md`（可読性原則）
- `~/.claude/skills/docwright/references/source-of-truth.md`（事実確認原則）
- `~/.claude/skills/docwright/references/boundaries.md`（他文書との責務分離）

## 対象と情報収集

対象読者は発注者・PM・開発者。実装の詳細（画面遷移・DB設計・処理フロー）は基本設計書・詳細設計書の担当であり、本文書には含めない。

要件は既存のIssue・チケット・ヒアリング記録・現行コードの挙動から拾う。**推測で要件を捏造しない**。裏付けが無ければ「未確認」と明示し、ユーザーに確認する。

## 新規作成

1. 既存の `docs/requirements/` 等の格納慣習があればそれに従う。無ければユーザーに保存先とファイル名を確認してから書き始める。
2. 次の構成で執筆する。
   - 背景と目的 — なぜこのプロジェクト・機能が必要か
   - 業務要件 — 業務フロー・利害関係者・達成すべき業務上のゴール
   - 機能要件 — システムが提供すべき機能の一覧
   - 非機能要件 — 性能・可用性・セキュリティ等の水準
   - 制約条件 — 予算・期限・技術的制約・法規制
   - 用語集 — プロジェクト固有語の定義

## 既存更新

1. 機能追加・仕様変更のたびに要件定義書が古くなりがちなので、コード・Issue・チケットとの差分を確認する。
2. 差分があれば該当セクションのみ更新し、確定済みの他セクションは書き換えない。
3. 用語集は新規登場した用語があれば追記する。

## 執筆後

自分では整合確認・可読性確認を確定させない。執筆完了をMainに報告し、`doc-verifier`・`review-doc-readability`への委譲を促す。
